# Team lifecycle regressions

Run `./pi/test-lifecycle-team.sh`. Requires the repository's existing `pi/node_modules`, Node with `node:sqlite`, jq, curl, tar, git, ps and the private lifecycle lab's existing tmux/Python dependencies. Does not install or deploy anything. Downloads the SHA-verified source pinned in `pi/upstream.json` and applies the repository patch only inside its retained temporary artifact directory.

Each callback has a first-runtime-alone control and a replacement case. Real Node processes register the same stable member through the actual `session_start` handler. The old runtime remains alive while the replacement overwrites its registration. The driver then dispatches the old runtime's actual `session_shutdown` callback or `team:before-exit` event and awaits its real `retireIfQuiet` transaction. An independent live sentinel has its own member ID.

Expected behavior: normal retirement makes the first member inactive; stale retirement leaves the replacement registration and sentinel unchanged. Replacement failures return exit 1 rather than treating the known defect as a passing test. The unfixed baseline failed both replacement cases by setting the replacement's `live` field to false while retaining its PID and process identity. Both normal controls passed. The regression also checks distinct registration incarnations in one process, stale retirement refusal, current-owner retirement, local eligibility and cancelled-ancestor registration refusal.

## Evidence and cleanup

The printed artifact directory retains source pin, patched source, role logs, registrations, before/after persisted state, callback observations, signal receipts, direct ps liveness records, exit receipts, summary and cleanup status. Observations happen before exit requests. The retirement driver never sends process signals. Each owned role accepts a private exit file and also has a 45-second self-exit watchdog. The shell waits for every child. A watchdog or nonzero child exit makes cleanup fail with exit 2. Admission runtime cases use only the documented private lab controls, including its identity-checked cleanup. Their separate retained lab directories contain before/after state, screens and status. The test checks all controller-tracked actors are dead after cleanup.

## Exact adapter boundary

The small MJS role file loads production TypeScript through the existing jiti dependency. It provides only an ExtensionAPI/context adapter: callback registration, an EventEmitter event bus, tool/command registration no-ops, an active-tool list, empty private session entries, a fixed private session ID, idle=true, pending=false, and a shutdown counter. Unexpected message delivery or journal append throws. There is no model, SDK session, tmux, GUI or TUI. No real user history is read. `TeamStore`, transactions, registration, process identity, retirement, filesystem state and stale writes are not mocked.

The retirement roles cover explicit shutdown and immediate quiet retirement, not deferred busy-message retirement or SIGKILL detection. Signal listeners record TERM/INT/HUP, and ps verifies replacement and sentinel processes still exist before fixture cleanup.

`shutdown.mjs` dispatches the actual team-extension shutdown hook with real owned Node workers registered as ordinary, resumed and nested members. It checks process death, independent-service survival, root resume, stale shutdown, stale launch reservation and delayed reserved-worker registration. The test retains `shutdown/owned-process-receipts.json` and `shutdown/cleanup.json`. These workers are OS-process fixtures, not model-driven Pi sessions. The separate `worker-root.mjs` integration below exercises real Pi tools and processes.

## Admission integration

`admission-runtime.sh` runs the actual reconstructed team extension after the actual opt-in guard in private real CLI/TUI instances. Cases cover:

- Conflict followed by Cancel. Later startup handlers still run, but the original saved conversation's team registration must remain byte-identical before and after contender exit. The unfixed baseline overwrote and retired it.
- Owned startup and ordinary chat, then `/new` and ordinary chat in the replacement session. The new session registers a fresh incarnation in its own team namespace. Shutdown under the old stopping receipt retires only its captured registration in the old namespace.
- Clean switch/reopen: the first root uses `/new` and remains alive in another session while a second PID reopens the original saved session. Both registrations stay live in their own namespaces. Quitting the first root cannot alter the reopened original registration.
- Normal managed `/quit` makes the owned registration inactive before any controller cleanup. An additional regression exposed that requiring open admission here left dead members marked live; the fixed path permits only incarnation-conditional cleanup.
- No guard, preserving ordinary legacy team startup/chat.
- Managed-unprotected startup induced by a private invalid sidecar path. Ordinary root chat still produces a real provider reply, without creating shared team state. The unfixed baseline created state.

The lab supplies isolated HOME and a saved session file shared by independently opened instances. Team's default namespace is `HOME/.pi/teams/<session-id>`, not each instance's cwd. The test discovers the actual private state files and checks real root PIDs.

`admission.mjs` uses the actual TeamStore and extension callbacks, with an EventEmitter and synthetic public admission responses. It tests pending/conflict/stopping/unprotected startup, changed canonical file or generation, missing/malformed responses, permanent fail-closed behavior after observing managed state, a stale send waiting for the real filesystem transaction lock, and paused/resumed automatic peer delivery. Its API adapter captures tool/command registrations, active tools, journal counts and message counts; context is idle with empty entries and a notify no-op. It does not mock the store or transaction. The lock-wait test creates/removes the private lock directory to represent contention. Stale receipt and delivery-pause tests are adapter tests, not full TUI proofs.

## Real worker integration

`worker-root.mjs` uses the private lab, the installed CLI and actual `subagent`/`subagent_message` tool calls. A loopback provider emits deterministic tool calls and records requests. The explicit candidate wrapper removes only the lab's `--no-tools` argument and sets the existing shell-ready delay to 20ms. A fixture tool extension records argv, admission, team state and process identity; it does not implement launching or ownership. The runner freezes and hashes one private lifecycle-core copy for the real-worker scenarios.

- `root-death` launches ordinary, completed-then-resumed and nested workers. It checks first-extension order, unchanged original-root JSON, each child's own session lock, and actual `RESUME_LIVE` provider work. A duplicate child opener cannot perform work. After root SIGKILL, all four workers must exit within five seconds; a separate service survives. Replaying the real worker argv after root death must refuse `LATE_CHILD_FORBIDDEN` before provider work.
- `window` SIGSTOPs an old worker, kills its root and opens a replacement root on the same saved root session. That replacement invokes actual `subagent_message` before the old worker exits. The same successor must wait for exclusive admission and then deliver `WINDOW_LIVE` to its provider. A module-load observation verifies the old process was still alive when the successor started; owned admission must observe it dead. No lease is removed or bypassed.

- `reload` starts a real worker with a nested worker, submits `/reload` in its pane, and verifies that the same requester PID is admitted with a fresh team incarnation while its nested worker exits. Subsequent input must reach the provider. The test cancels the fixture's deliberately held response before that input.

`worker-admission.mjs` separately covers managed denial, stale/lost receipts, explicit legacy behavior and nested byte-for-byte metadata inheritance through the production launch-admission helper. It supplies only admission responses and a file-existence fixture.

Evidence includes provider requests, per-PID receipts, phase observations, root-death timing, successor window receipts, lab state and cleanup receipts. Fixture-owned workers are identity-checked before failure cleanup; direct test children are reaped and every lab actor must be dead after cleanup. Synthetic loopback work does not use account quota.

## Startup order and admission contract

Explicitly load `pi/agent/lifecycle/session-lifecycle.ts` before the patched `team-extension.ts`. The guard must register its public responder before team's factory query and finish its earlier `session_start` handler before team's startup handler. This gates this extension's startup/shared effects, not arbitrary extension imports or unrelated factories.

Team emits the synchronous public `session-lifecycle:admission` query without importing guard code or private symbols. Initially no responder means unmanaged legacy behavior. Any observed responder disables that fallback for this extension instance. Missing, malformed or multiple replies then deny work. An owned receipt is copied at startup; current canonical file and generation must match before work. Each extension-owned TeamStore retains its captured receipt and rechecks admission before creation and inside the existing transaction lock. Commands, sends, quiet retirement, context injection and automatic delivery pause when admission is unavailable. Explicit shutdown cleanup has the narrow exception below. The guard may allow ordinary unprotected root chat; team does not block that chat.

When the earlier guard shutdown handler closes admission, explicit shutdown may call `cancelTree(member, incarnation)` and `retire(member, incarnation)` using the registration token captured at successful startup. Both compare the token under the existing transaction lock through a local store. Cancellation fences the captured subtree against delayed starts; retirement only changes the matching member's `live` field. Neither exposes arbitrary mutation through the admission exception. A cancelled startup has no registration token. A stale token cannot cancel or retire a replacement, including one registered while cleanup waits for the lock. Registration, sends, arbitrary updates, desired-mode writes and quiet retirement retain their admission checks.

Adapter tests assert admission closure blocks new work before shutdown, then permits only exact-registration cleanup. They also race closed-admission cleanup against replacement registration and verify all other guarded write methods remain blocked.

`abandoned-root.mjs` starts a real owner process that registers, cancels its tree and exits without retiring. With managed-owned admission, the replacement invokes the actual extension startup hook. The test verifies the old PID is absent while persisted `live` remains true, then checks successful successor registration, stale resume/callback rejection and preserved descendant cancellation. Live-owner and denied-admission controls cannot reopen the root. Its `old-owner.json`, `replacement.json` and `cleanup.json` retain the process and state receipts. This tests the team boundary with a synthetic public admission responder, not the guard's ownership verification itself.

## Focused review regressions

`reload.mjs` dispatches actual child shutdown/start callbacks for reload and same-file resume, verifies real descendant process exit, and checks stale-launch and cancelled-ancestor fencing. `resumed-name.mjs` exercises saved-member reservation and named routing with retired history plus genuinely ambiguous live peers. `arena-admission.mjs` verifies rejected arena work leaves generation, leases and pending delivery unchanged, including admission loss at the real transaction lock, and checks own-token-only suspension cleanup after revocation.

`root-replacement.sh` dispatches the actual `new` and `fork` shutdown reasons in real Node role processes. A second PID must register the original root while the first PID remains alive and receives no signals. This is callback-boundary coverage for both reasons; the separate `switch-reopen` CLI scenario specifically types `/new`, not `switchSession`/resume.

`batch-retirement.mjs` counts real TeamStore transactions for sixteen historical descendants. It expects one cancellation write plus one retirement write. Its replacement control commits a changed incarnation through the real update path immediately before retirement; the captured old token must not retire it. Its survivor control leaves a real owned tmux pane open through the supplied close callback, expects verified cleanup to fail without retirement, then removes and verifies that private pane during fixture cleanup.

## Production scope and remaining gaps

Each successful `register` creates and returns a fresh incarnation, even for identical PID/start text. Both quiet-retirement paths retain their captured-incarnation and local eligibility checks.

`team-arena.ts` exports `cleanupTeam(store, member, close, incarnation?)`. Arena uses the existing unfenced cancellation entry point. Normal shutdown supplies its captured incarnation, excludes the caller from signalling, and waits for identity-checked process/pane cleanup before retiring the caller. Cleanup rechecks member incarnations using one fresh snapshot per check and retires the captured descendants conditionally in one transaction after verification. Reload/resume shutdown omits only the matched requesting member from new cancellation markers; it does not clear any existing ancestor/member cancellation, and descendants stay fenced. A matching retired root can reopen its own cancellation marker. A matching root whose recorded PID is absent can also reopen it after cancellation interrupted retirement; the check requires ESRCH from a zero-signal liveness probe. Live/reused PIDs, missing ownership metadata and other probe errors stay fenced. Resume tokens must still match inside the transaction. Descendant markers remain to block delayed startup. A cancelled ancestor still blocks registration. Launch and resume capture the parent incarnation before asynchronous preflight and pass it to reservation, whose registration rechecks it under the transaction lock.

`worker-lifecycle.ts` captures managed admission before launch preparation and rechecks it before command delivery. Managed pending/conflict/stopping/unprotected states cannot launch workers; missing responders stay denied after managed admission was observed. With no guard or ownership metadata, the explicit legacy path remains available. Launch and resume put the deployed lifecycle extension first among `-e` arguments and pass transient `PI_LIFECYCLE_OWNER` containing the original root PID, trimmed `ps lstart`, canonical saved file and generation. Nested workers forward those exact JSON bytes while retaining their own session lock. Arena captures the same admission before suspension changes and rechecks it while waiting for the team lock. Revocation still permits removal of its own captured suspension token, but no other shared mutation. Named direct messages resolve among eligible live recipients, so a retired same-name history entry does not make one live resumed worker ambiguous. No guard event, broker or persistence schema was added.

Remaining boundaries: launcher rollback still calls unconditional `update(id, fields)`; send/pending routing uses stable sender IDs. Shutdown does not await every tool execution before its reservation exists, so an empty launch pane can remain briefly. Late worker startup must refuse work when its original root has died. In-process hooks cannot protect against parent SIGKILL; the separate lifecycle helper supplies that enforcement. No deployment is needed.
