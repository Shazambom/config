# Evidence-bound operating lessons

These corrections came from actual campaign roadblocks. They establish checks to perform, not performance gains. Keep campaign-specific IDs, logs, and private paths in the private ledger. Revise these rules when new evidence contradicts them.

## Human-fixed settings are not tuning candidates

Root incorrectly treated reasoning effort as an optimization variable despite the human's comparator-matching constraint, and the skill itself permitted that mistake. Reasoning effort is a human-dictated invariant. Remove the contradictory permission rather than relabeling the resulting trials exploratory. At session start/resume record each human pin, its source, effective override/precedence, and proof; before every launch verify it and the separate eligible-variable allowlist, then check actual recorded values after exit. "Optimize settings" does not authorize changes to human pins. A violation keeps its official grade and spent charge but is protocol-invalid, excluded from winner selection, and cannot be promoted, refunded, or automatically rerun. Stop launches, correct records explicitly, and ask the human about resumption.

## Verify activation, not just configuration or task success

A fresh container omitted `ps`. Ownership protection warned of failure, and OM workers/task cues were not admitted. A passing solver grade and an enabled setting did not establish healthy activation. Verify required executables, ownership/readiness, and actual worker admission once for the frozen image; retain diagnostic logs and reuse that verified image. If diagnostics are missing, activation remains unknown. Do not disable guards or attribute performance to OM without evidence.

## Check shell configuration side effects through the actual tool

A login-profile shell prefix selected the intended Python and passed official grading, but produced an ASCII decode failure; cross-image native-tool checks also found Node 22 absent from PATH. A grade pass or import-only probe did not establish preservation of critical executables, text encoding, or cwd. Check actual native-tool input/output on the intended images, using the existing qualification path rather than another framework. The repaired candidate preserves the selected environment by appending the saved original PATH after the profile PATH, selects a verified UTF-8 locale, and preserves cwd. Native-tool fixtures passed on the two checked images; there is no paid performance evidence for that repair yet. Treat the coherent repair as a bundle, not independent-factor evidence, and do not claim global portability or speed from these fixtures.

## Verify what accepted settings actually change

Setting names and accepted values do not prove behavior or activation. In installed Pi 1.0.4, explicit WebSocket selection still permits SSE fallback, contrary to root's initial claim; selected-runtime source inspection caught this before a trial, and root corrected the ledger/chat. Changing `codemode.mode` alone has no effect while `defaultActive: false` leaves codemode inactive. Document activation and coherent `defaultTools`/mode prerequisites before testing; treat a necessary prerequisite bundle as a bundle, not independent-factor evidence. Inspect the actual runtime branch, distinguish accepted setting, effective change, and measured outcome, and reject unsupported hypotheses early.

A context-pruning comparison also reduced the first prompt but incurred an extra model call that outweighed that benefit. Evaluate end-to-end task correctness, time, and total tokens rather than declaring improvement from one smaller prompt. Do not generalize that result to every pruning policy.

## Check whether the task exercised the capability

Four valid Git-task runs remained Bash-only; one of them exposed fourteen file tools directly. Check task applicability and actual calls first; unused tools cannot support a tool-use performance conclusion. `toolsAdded`/`toolsRemoved` establish declaration changes, not usage. Prose tool sections may omit native tools lacking `promptSnippet`, so inspect actual declarations rather than inferring absence from prose. A raw MCP fixture pass verifies that library path only, not actual Pi discovery, codemode access, or model use.

## Restore package-manager state, not only versions

An official grader's setup failed when image preparation left package holds in place. A subsequent comparison changing only restoration of the original HOLD selections passed. Preserve and verify package HOLD selections alongside version pins; do not assume restoring `/etc/apt`, package lists, and installed versions restores package-manager behavior. Keep the attribution limited to that observed setup correction, not general solver performance. Retain diagnostics and reuse the exact qualified image/dependency bundle rather than repeating broad preflight or endless mock-harness probes.

## Bound parallelism by authorization and review

Sequential trials remain the default. When the human authorizes up to two simultaneous attempts, use different tasks with one frozen profile, reserve both against unchanged total/sub-budgets, and monitor aggregate resources/cost. Review both real results before selecting a new configuration/batch; do not refill a completed slot early. Treat concurrent timing as potentially confounded rather than a clean speed comparison. This authorization is not a sweep, automatic retry, or larger trial allowance.

## Stop optimizing a saturated task

A short task became a diminishing-returns target before its authorized trial ceiling; the user closed that campaign and requested longer, more discriminating benchmark screening. Freeze the best verified profile and capability tradeoffs instead of treating unused budget as an obligation or a plateau as automatic code-escalation permission. Keep the old campaign closed, retain its task as a cheap regression, and require separate human authorization and ceilings for new tasks/harness attempts. One Pi/Codex pair per candidate ranks provisional gaps, not reliability or general parity. Long elapsed work does not by itself establish long-context demand, and a short-task OM-off winner does not settle settings for long tasks.

## Resume from compressed history, not a blank experiment list

Keep one authoritative project-level historical index in the existing ignored workspace and read it before hypotheses/preparation on every start/resume. Link each compact hypothesis/family/session entry to full ledgers and evidence, keeping scope/invariants/profile versions, factors/trial IDs, outcome/confidence, status, spent/unused budget, pending work, next action, and an explicit retest condition. Reconcile uncertain counts from original records. New sessions do not justify repeating work; record changed conditions, a new hypothesis, or authorized confirmation before a retest. Keep negative findings task-scoped and corrections visible; invalid trials remain charged and excluded. Update at checkpoints/handoff without blocking ready work. Do not turn the index into raw transcripts, another memory service, or a replacement for evidence.

## Evaluate long-running tools and settings on sustained-work outcomes

Bounded tasks can expose bookkeeping or context overhead while missing a tool or setting's benefit during sustained work. They are poor grounds for rejecting capabilities intended to preserve progress, recover after interruptions, or keep an agent on task. Record the intended horizon, activation evidence and the user's acceptable overhead before interpreting results. When overhead is minimal and accepted, do not require a speedup or exhaustive proof of a hard-to-benchmark benefit. Retain provisionally unless relevant evidence establishes a regression against a valid baseline in sustained focus, completion, recovery or required verification. Correctness and state-integrity failures remain real failures; this is not immunity from negative evidence. Report untested benefits as unproven, not wins. Long wall time alone does not prove a long decision sequence or context-recovery demand. Use existing configuration and simple capabilities first; building automatic activation can cost more than the small overhead it avoids.

## Self-reflection method

Separate abstract tenets from technical details before recording a lesson. State an abstract lesson as a transferable decision principle with its applicable conditions, not a rule tied to the triggering feature or tool. Check comparable situations and avoid unsupported universal claims. Keep project-specific mechanisms, exact APIs and regression evidence in scoped technical records. Prefer refining a general principle to accumulating incident-shaped exceptions.

Ask "What could I have done better?" after mistakes, corrections, changed behavior, unexpected checks, and each trial. Name the assumption, missed evidence/instruction, earlier preventive check, confidence error, premature stopping, or mismatch with the request. Correct affected records explicitly first. Retain only a concrete, verified next-time rule with its cause known or marked unknown. Merge/revise lessons rather than accumulating an incident diary. Record skill/prompt hashes and any instruction change in the private campaign so guidance revisions cannot silently contaminate comparisons.
